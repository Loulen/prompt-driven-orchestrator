# Triggers + autonomie gagnée par la confiance (révise « pas d'auto-merge, jamais »)

**L'interdit « pas d'auto-merge vers main, jamais » est révisé en *Deliberate, then autonomous (trust-earned)* : l'autonomie devient une cible atteignable, pas un interdit.** Sans cette révision, les Runs récurrents (#104, #137) — un auditeur qui crée des issues `ready-for-agent`, un fixer qui les ramasse sur cron — buteraient sur un « jamais » qu'ils contredisent frontalement. Le défaut reste délibéré, humain dans la boucle.

**(a) L'autonomie est une propriété du pipeline, jamais du runtime ni du Trigger.** Le « jamais » ne porte plus sur l'*effet* (merge, PR, cleanup) mais sur son *origine* : **le runtime ne déclenche jamais d'action durable de lui-même** ; si elle se produit, c'est qu'un **nœud du pipeline** l'exécute — choix explicite du designer, versionné et auditable. Conséquence : un pipeline auto-shippant se comporte à l'identique lancé à la main ou par Trigger. Contre *une termination-policy sur le Trigger* (cases « auto-PR / auto-merge » appliquées par PDO après le Run) : ça scinderait le comportement manuel/déclenché et placerait les actions effrayantes hors du graphe auditable.

**(b) Un Trigger est start-only** : il lie une condition (heartbeat cron + guard script optionnel) à un template de Run et ne décide **jamais** de la terminaison. **Un firing = un Run** (la multiplicité passe par une boucle `collection`). **Idempotence déléguée au monde extérieur** : PDO ne tient aucun `fired_keys` ; le pipeline mute l'état qu'il poll (un label GitHub sert de registre de dedup). Un moteur de dedup interne *devinerait* l'intention — on préfère le guard cheap + dedup externe (*Sharp tool*, ADR-0001), au prix assumé qu'un guard mal configuré sur un pipeline qui ne mute rien boucle (borné par le skip). Safety : **skip de recouvrement par-Trigger** (le cap seul empêche l'effondrement tmux mais pas l'empilement sémantique : re-fire sur la même issue pendant que le fixer la traite) et **cap global de sessions**, avec attente au niveau nœud, managers exemptés. Le guard gate **avant** le spawn — un cron seul ferait tourner un Run complet par tick juste pour découvrir « rien à faire ».

Persistance en tables SQLite (`triggers`, `trigger_fires`) : config + état de scheduling **mutable**, réécrit à chaque tick, donc pas un artefact canvas-backed — le YAML sur disque serait le mauvais fit, et cela n'entame pas l'event-sourcing, qui reste la vérité du *Run*.

**Limites acceptées.** Daemon best-effort v1 (les Triggers ne firent que tant que le process vit ; service persistant → #156). Fires manqués **forward-only**, correct par construction (un poll forward voit tout le travail accumulé). **Imbrication/chaînage de Triggers exclue** : les pipelines se couplent par le monde extérieur, jamais par un wiring interne. `next_fire_at` en **UTC canonique**, comparaison de tick tz-normalisée, cron interprété en UTC. Un panic de tick est **isolé** (la boucle survit) ; liveness via `GET /triggers/health`.

## Addendum (#372) — Ré-activer un Trigger recalcule `next_fire_at` vers l'avant

**Ré-activer un Trigger (`PATCH {enabled: true}`) repart au prochain slot à venir, sans rattraper le slot manqué pendant la désactivation** — un Trigger dormant depuis des jours ne fire donc pas d'un coup. Le comportement antérieur (le slot devenu passé était vu comme *dû* au tick suivant) était un rattrapage implicite né d'une omission. Un fire manuel « Run now » (ADR-0027) laisse au contraire `next_fire_at` intact : le heartbeat cron possède le planning. Dans les deux cas, **un `next_fire_at` périmé n'est jamais une raison de firer**.

**Asymétrie assumée** : deux chemins conservent le rattrapage du slot courant (jamais un backfill des slots antérieurs) — le **boot du daemon** et la **dé-pause globale** (#348). La divergence est délibérée : une ré-activation manuelle par-Trigger est un « redémarrage propre » ; le boot et la dé-pause, un « on reprend où on s'était arrêté ».

**Couture d'implémentation à préserver** : un unique stringifieur `CronSchedule::next_fire_utc` (seul point où `next_fire_at` est stringifié, ce qui rend le `…Z` canonique inviolable au niveau *type*) et une unique matrice `recompute_next_fire(now, Transition)` où chaque transition de cycle de vie choisit *explicitement* avancer / laisser / effacer. Le `match` exhaustif force toute transition future à trancher — plus d'omission silencieuse comme celle qui causait ce rattrapage.

## Addendum (#348) — Pause globale des Triggers (kill-switch daemon-wide)

**La pause globale est une suppression start-only**, de la même classe que le skip de recouvrement et le cap de sessions : le runtime n'initie toujours aucune action durable, il en *supprime*. L'invariant (a)/(b) tient. Le flag court-circuite le tick *après* le heartbeat de liveness, *avant* `due_triggers`.

**Le `enabled` par-Trigger n'est jamais muté** : « restaurer l'état antérieur » est donc gratuit (rien à sauvegarder), robuste au redémarrage, et cohérent cross-clients (broadcast WS). Pause globale et `disabled` par-Trigger sont **deux canaux orthogonaux**.

**Aucune transition de cycle de vie n'est ajoutée** pour la dé-pause : pendant la pause `due_triggers` n'est pas appelé, donc `next_fire_at` reste gelé dans le passé, et le tick ordinaire suivant le voit `≤ now` et fire une fois via l'arm `CronTick` existant. La pause est une **grille daemon-wide, pas un état du Trigger** — toute PR qui toucherait `recompute_next_fire` ou l'enum `Transition` pour ça serait un signal d'erreur de conception.

**« Run now » fire pendant la pause** (derrière une confirmation UI) : le chemin manuel est disjoint du tick et ne consulte aucun flag. Le précédent 409-on-disabled d'ADR-0027 ne transfère pas — le remède d'un `disabled` est local, celui d'une pause est global (dé-pauser ré-arme *tous* les Triggers), et le geste manuel est justement l'échappatoire assumée.
