# Le Merge devient un nœud first-class, plus auto-spawné

Première itération (CONTEXT.md "Merge Resolver") : un rôle `code-mutating` built-in, **auto-spawné** par le runtime quand un `git merge` entre branches `code-mutating` parallèles produit un conflit. Toggle `auto_merge_resolver: enabled | disabled` au niveau pipeline. Cette formulation a deux défauts : (1) elle introduit de l'orchestration ambiante (le runtime décide de spawner sans que le designer l'ait demandé), ce qui contredit *Sharp tool* (ADR-0001) — le designer ne *voit* pas la barrière de synchro dans son DAG ; (2) elle ne couvre que le cas conflit, pas la barrière elle-même : un fan-out parallèle de N branches `code-mutating` n'avait aucun nœud explicite pour rassembler, c'était implicite. Le besoin a explosé avec le parallèle obligatoire des boucles `collection` (ex-ForEach), qui rend la barrière + fusion un pattern *de premier ordre*, plus une exception.

**Décision : le `Merge` devient un nœud first-class du DAG, type `code-mutating` toujours, à placer explicitement par le designer.** Sa forme : 1 input port `branches: repeated` (accumule N edges parallèles), 1 output port `merged` (artefact résumé du merge avec frontmatter `conflict_count`, `branches: [...]`, et corps narratif). Sémantique : (a) barrière **edge-centrée** sur ses entrantes (détaillée ci-dessous) ; (b) forke un sous-worktree depuis la branche du Pipeline Run ; (c) tente `git merge` sur chaque upstream qui a une branche dédiée (= les `code-mutating`) ; (d) si conflit → spawn Claude Code dans le sous-worktree, qui lit les artefacts du Blackboard pour reconstituer les intentions, résout, commit ; (e) si pas de conflit → écrit un summary trivial *"merge auto, no conflict"* + commit, sans LLM. Le toggle `auto_merge_resolver` disparaît. Le Merge auto-spawné disparaît.

## La barrière est edge-centrée (amendée avec ADR-0011)

La formulation initiale était node-centrée : le Merge était prêt quand *tous* ses producteurs d'edges étaient `Completed`. Avec les edges conditionnels d'ADR-0011 (routage `when:`/`else` en multi-match), une branche peut être **routée ailleurs** et ne jamais spawner : son producteur ne devient jamais `Completed`, et la barrière node-centrée attendait alors **éternellement** une branche qui ne viendra jamais — un **stall silencieux** du Run. (Régression observée par un test couche 5 : `classifier` fan-out `severity=high` → hotfix, `security=true` → security-review, `else` → backlog ; artefact `high + true` → hotfix et security-review firent, la `else` backlog ne spawne jamais → le Merge attend backlog pour toujours.)

La barrière est donc un cas particulier de la règle de convergence générale (pas un traitement spécial du `merge`) :

- Une edge entrante est **résolue** quand elle a soit **firé** (producteur `Completed` + garde satisfaite, ou edge inconditionnelle), soit est **morte** (producteur `Completed` mais l'edge n'a pas firé — `when:` faux, ou `else` avec une sœur du même port qui a matché ; ou bien le producteur est lui-même mort).
- Un nœud est **mort** pour ce Run s'il a des edges entrantes ET qu'elles sont **toutes mortes**. La mort se **propage** de l'amont vers l'aval : un producteur complète → on évalue ses edges sortantes (firées/mortes) → tout nœud aval dont *toutes* les entrantes sont désormais mortes devient mort, y compris un `Merge` dont les `branches` sont toutes mortes, et y compris `End`.
- **Prêt** : un nœud (Merge inclus) est prêt quand **toutes ses edges entrantes sont résolues** (firées ou mortes) et qu'**au moins une a firé** ; il spawne en consommant **uniquement les branches firées**. Le Merge part dès que ses branches vivantes ont complété, ignorant les branches mortes.
- **Merge à zéro branche firée** (toutes mortes) : le Merge est lui-même mort et **sauté**, comme tout nœud tout-mort — **tant que `End` reste atteignable** par un autre chemin vivant.
- **Jamais de stall silencieux** : si la cascade de mort rend `End` inatteignable (plus aucun chemin vivant n'y mène), le Run **halt explicitement** dans un état diagnosticable (`run_halted`, message « unrouted »), jamais figé en silence. C'est le principe posé par ADR-0011 pour l'épuisement de boucle (« exhausted — unrouted »), étendu à toute convergence.
- **`End` est une convergence, pas un premier-arrivé (amendement #394).** Atteindre `End` **complète le Run** : c'est la convergence terminale, soumise à la **même** barrière que le `Merge`. Le Run ne passe `completed` que lorsque **toutes les edges entrantes de `End` sont résolues** (firées ou mortes), pas dès la première. Un fan-out parallèle plat (`start→A→end`, `start→B→end`, sans `Merge` ni `collection` entre A et B) atteint `End` par deux edges indépendantes : la **dernière** branche vivante à arriver complète le Run ; chaque arrivée antérieure est un no-op. Avant #394, `End` était le **seul** point de jointure à firer sur sa première entrante — la branche rapide basculait tout le Run en `completed` et abandonnait la branche sœur restée `running` pour toujours (son `pdo complete` tardif → 409 « resume the run first », `resume_run` → no-op sur un run terminal), en contradiction directe avec la règle générale ci-dessus. Le `Halt`-sur-`End` (edge avec `reason:`) reste, lui, un premier-arrivé : c'est une sortie *bloquée* explicite, pas une complétion.

**Conséquence sur `branches: repeated`.** Le port accumule les branches **réellement firées** (compte dynamique, pas la liste statique des upstream déclarés). Une branche morte ne produit ni artefact ni sous-worktree/branche git, donc elle est **naturellement** exclue du `git merge` et du frontmatter `branches: [...]` : chaque nœud qui a réellement tourné est mergé, le `merged.md` reflète ce qui a convergé.

**Périmètre.** Cette barrière edge-centrée couvre la convergence **hors boucle**. La convergence **par-lap dans une boucle bornée/collection** (état d'edge/nœud par itération) est **différée** (#148/#151) ; l'état de résolution est porté par-Run et reste compatible avec une future clé par-itération.

**Pourquoi.** Choisi contre *"garder l'auto-spawn et y greffer les barrières des boucles collection"* parce que ça aurait empilé deux mécanismes implicites (barrière + résoluteur) que le designer ne voit ni ne configure — incompatible avec *Sharp tool*. Contre *"deux nœuds distincts `Merge` (code) et `Join` (doc-only)"* parce que la sémantique "rassembler N branches" est unique du point de vue designer : il wire ses N branches vers le port `branches` et le runtime fait le bon choix selon le type des upstream — forcer deux nœuds pour le même geste est friction inutile. Contre *"spawn LLM systématique pour traçabilité"* parce que le coût (un Claude Code par convergence, même triviale) écrase le bénéfice ; le summary trivial sans LLM suffit pour l'audit. Sur la barrière : contre *garder la barrière node-centrée et exempter manuellement les branches `else`* — la liste des branches « optionnelles » dépend de l'artefact runtime, pas du graphe statique, impossible à fixer à l'édition ; la résolution edge-par-edge est la seule formulation qui reste correcte quel que soit le routage conditionnel observé. Contre *laisser le Run figé et compter sur un timeout* — un stall silencieux est indiagnosticable ; un halt explicite « unrouted » est routable par le Pipeline Manager. Conséquences : les pipelines qui s'appuyaient sur l'auto-spawn cassent — la migration doit insérer un Merge downstream de chaque fan-out `code-mutating` détecté, sinon le runtime n'a plus rien pour résoudre les conflits. Diagnostic info-only dans l'éditeur si fan-out `code-mutating` sans Merge downstream (ADR-0001 : lint info-only autorisé).
