# Configuration d'instance : store SQLite singleton + précédence `stored → env → default`

> **Amendé par ADR-0046** : l'instance n'est plus le tier le plus haut pour tout réglage — le harnais agentique en compte deux au-dessous d'elle (Run, Projet) — et son défaut de modèle devient un défaut **par harnais**. La précédence `stored → env → default` de chaque réglage est inchangée.

**La valeur stockée par l'UI gagne sur la variable d'environnement, jamais l'inverse.** Une page de réglages qu'un env écrase silencieusement est un **no-op pour les opérateurs mêmes pour qui elle est construite** (l'install prod exporte typiquement `PDO_SESSION_CAP` via systemd) : ils changent la valeur, rien ne se passe, aucun feedback — pire qu'une absence de page. Les deux ordres gardent la suite de tests verte (aucun test n'écrit de stored), donc **les tests ne départagent pas** : c'est l'intention produit qui tranche. L'env devient un **bootstrap** consulté quand le stored est `NULL` ; le défaut est le plancher. Le risque symétrique — un opérateur qui *épingle* délibérément par env — est désamorcé par la **divulgation** : `GET /settings` renvoie par champ `{ effective, source, stored, env, default }` pour que l'UI **révèle** un env masqué plutôt que de l'ignorer en silence.

Le store est une table SQLite **singleton** (`instance_config`), calquée sur celui des Triggers : config + état mutable, pas un artefact canvas-backed — mauvais fit YAML. Ajouter un réglage futur = une colonne + un champ.

**Hors scope explicite (décision-frontière).** Toute option « le manager vérifie périodiquement le pipeline » reste **exclue** : elle réveillerait le manager depuis le runtime, renversant *Pas de polling actif* et touchant la frontière d'origine-de-l'autonomie d'ADR-0012 (l'autonomie est une propriété du *pipeline*, jamais du runtime). C'est une décision humaine séparée ; une page de réglages qui la câblerait construirait le couplage par la porte de derrière.

## Amendement #471 — un réglage peut aussi *sortir* de cette table

`image_source` et `dockerfile_path` quittent `instance_config`, `GET`/`PUT /settings` et l'écran de réglages. Depuis #467, la source d'image d'un Run se configurait à **deux** endroits — le profil de staging, qui gagne, et ces réglages, qui servaient de repli. **Un axe par écran** : les réglages répondent « quel profil un Run prend par défaut », un profil répond « ce qu'est le sandbox ». Le symptôme était visible — une note de quatre lignes sous le champ, qui renvoyait vers un autre écran ; **quand un réglage a besoin d'un paragraphe pour expliquer sa relation avec un autre écran, il est sur le mauvais écran.** Coût mesuré nul : sur la seule instance existante, les deux champs n'ont jamais porté de décision.

Quatre conséquences, dont deux amendent les règles générales ci-dessus :

- **La précédence du sandbox perd le tier `stored`** : `profil (par Run, gelé) → env → défaut`, où le défaut est une **constante de la couche de défauts de profil**. Un défaut n'a donc pas besoin d'être réglable *ici* pour exister — c'est ce que le raisonnement de #467 avait confondu.
- **Le tier env survit à la disparition du tier stored**, ce qui inverse localement la lecture « l'env est un défaut de bootstrap » : `PDO_SANDBOX_IMAGE_SOURCE` et `PDO_SANDBOX_DOCKERFILE` deviennent le **seul** levier instance-wide, une instance headless fraîche n'ayant que des profils virtuels et pas d'UI. Ce qui disparaît est le champ et l'écran, pas la variable.
- **Retirer un champ de `PUT /settings` est un `400` qui le nomme**, jamais un `200` qui l'ignore. Le projet n'a aucun objectif de compatibilité ascendante — la casse se signale par le semver et le CHANGELOG, pas en gardant des champs morts (précédent : ADR-0031 a renommé des profils **sans alias**) — mais un client qui envoie un champ retiré doit l'apprendre. Corollaire symétrique : un champ simplement **inconnu** reste ignoré par serde.
- **Une valeur stockée devenue inopérante se dit une fois.** Les colonnes ne sont pas droppées, elles deviennent **inertes**, et le boot émet **un** warning qui les nomme et renvoie vers le profil à éditer. Une valeur que l'utilisateur a posée ne doit jamais cesser de compter en silence.

Interagit avec ADR-0012 (le cap de sessions est *la* primitive de sécurité contre l'effondrement tmux) et *Sharp tool* (ADR-0001) : la page **configure**, elle ne prescrit pas — au plus un avertissement ambre au-delà du seuil d'effondrement, jamais un blocage.
